# glspinner-implement

## このスキルの立ち位置

このスキルは実際にソースコードを書く・変更する作業そのものを担当する。設計判断（クラス構成をどうするか等）はできれば`glspinner-design`で先に済ませておきたいが、変更が小さく設計判断の余地がほとんどない場合（既存パターンに則った具象クラスの追加、バグ修正相当の変更など）は、このスキルの中で軽く判断してそのまま進めてよい。設計の論点が複数あり後戻りコストが高そうな変更（新規`BaseXxx`階層を作る、レンダリングパイプラインの配線を変えるなど）は、着手前に`glspinner-design`に切り替えることをユーザーに提案する。

## 実行手順

### 1. コンテキストダイジェストの取得

`/glspinner-context <対象トピック>` を実行する。関連ファイル・お手本実装・適用すべき設計パターン・規約上の留意点を把握してから着手する。

### 2. 実装

- ダイジェストで挙がった「お手本実装」と同じ構成・命名・フォーマットに合わせる。迷ったら既存の類似クラスをそのまま模倣する方が、独自判断で規約から外れるより安全。
- 新規にインターフェース/抽象クラス/具象クラスを増やす場合は、`.claude/rules/general.md`のファイル配置ルールに従い、対応するディレクトリに配置する。
- タスクに直接関係しない範囲のリファクタリングは行わない（システムプロンプトの一般方針どおり）。ただし、変更対象のファイルが明らかに規約から外れている場合は、その旨をユーザーに一言伝えるに留め、無断で広範囲を書き換えない。

新規コードを書く際、一般的なTypeScriptのベストプラクティスとglspinner固有の規約が食い違う箇所がいくつかある。一般常識に引っ張られて規約を破らないよう特に注意する（`.claude/rules/general.md`・`.claude/rules/operation-base.md`参照）:

- **等価比較は多数派として`==`/`!=`を使うが、`SceneNode.ts`や`RenderTarget.ts`のように`===`/`!==`が混在するファイルもある**（プロジェクト全体で厳密に統一されているわけではない）。新規コードでは、触っているファイル内の既存の書き方に合わせるのが安全（ファイル単位では概ね統一されている）。詳細は`.claude/rules/general.md`「未解決・揺れがある事項」。
- **private/protectedプロパティにアンダースコア接頭辞を付けない**（`this._foo`ではなく`this.foo`）。
- **JSDocコメントを書く慣習がない**。関数・クラスの説明コメントは書かず、コメントを書くのは「自明でない理由の説明」または「無効化したコードを消さず残す」場合のみに限定する。
- **無効化する既存コードはコメントアウトで残す**（削除しない）。新たに一時的に無効化する必要が出た場合も、この既存運用に合わせる。
- **`Operation`+`Base`パターンを適用するかどうか**: 差し替え可能なサブシステムの入口（状態を持ち、DI/モック差し替えの対象になりうるもの）にのみ適用する。静的メソッドのみのユーティリティや値の集合を定義するだけの`Constants`ファイルには適用しない（`.claude/rules/operation-base.md`）。適用する場合も、`~Device`や`~Buffer`のように`Base`側が共通実装を持たない「薄いBase」もあれば、`~Material`のように共通実装を持つものもあるので、対象ファミリーの既存パターン（`.claude/rules/`配下の該当ファミリーファイル）に合わせる。
- **新しい定数集合を追加する場合**は`export const XxxConstants = {...} as const;` + `export type Xxx = typeof XxxConstants[keyof typeof XxxConstants];`という既存パターンに合わせる。

### 3. 検証

変更内容に応じて、可能な範囲で検証する:

- **型チェック**: TypeScriptの変更なら `tsc`（`npm run build`相当の型チェック部分、あるいは対象ファイルのみ`npx tsc --noEmit`）で型エラーがないか確認する。
- **既存テストへの影響**: `tests/`配下に対応するテストがある場合（`math/`・`color/`・`scene/`の一部）は `npm test` で実行する。新しいロジックを追加した場合、それが純粋なロジック（math/color系など）ならテスト追加を検討し、必要なら`glspinner-test`スキルに引き継ぐ。
- **WebGL依存部分**: `webgl/gl/`・`scene/renderer/`などWebGLコンテキストに依存するコードはユニットテストで検証しづらい。この場合は`run`/`verify`スキル（ブラウザで実際に動かして確認するもの）を使うか、少なくともユーザーにブラウザでの目視確認を促す。型チェックが通っただけで「動作確認済み」と報告しない。

### 4. 完了後

何を変更したか、検証で何を確認し何を確認できていないか（例: 型チェックのみでブラウザ未確認等）を簡潔に報告する。規約や設計との整合性チェックを別途しっかりやりたい場合は`glspinner-review`、細かいフォーマットの見直しは`glspinner-tidy`、ドキュメント反映が必要なら`glspinner-document`を案内する。
