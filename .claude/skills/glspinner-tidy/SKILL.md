# glspinner-tidy

## このスキルの立ち位置

`/simplify`は再利用性・簡潔性・効率という「意味のある改善」を扱う。このスキルはそれとは別で、**意味を一切変えない見た目だけの整形**に限定する。glspinnerにはESLint/Prettierが導入されておらず（`.claude/rules/general.md`冒頭に明記）、フォーマットの統一は人力でやるしかない。このスキルはその機械的な整形作業を担当する。

ロジックの変更・変数名の意味変更・条件分岐の並べ替えなど「動作やコードの意図に踏み込む」判断はこのスキルの範囲外。そういう変更が必要だと気づいた場合は、勝手に行わずユーザーに`glspinner-review`または`/simplify`の利用を提案する。

## 実行手順

### 1. 規約の確認

`.claude/rules/general.md`の「フォーマット（インデント・空白・改行・セミコロン等）」「import / ファイル配置」「未解決・揺れがある事項」セクションを読む。対象クラスが特定のファミリー（`~Material`等、`general.md`冒頭の索引参照）に属する場合は、そのファミリーファイルの「固有の揺れ・例外」節も確認する（例: `render-target.md`は`RenderTarget.ts`が`===`/`!==`を使うことを明記している）。`.claude/rules/`が存在しない、または対象の観点が未記載の場合は、同じディレクトリ内の他ファイル2〜3個を読んで実態を確認し、それに合わせる（推測であることを明記する）。

### 2. 対象ファイルの整形

`.claude/rules/general.md`に明記されている具体的なルールに沿って、規約から外れている箇所を直す:

- **インデント**: 半角スペース4つに統一する（`src/scene/mesh/UnlitMesh.ts`18行目のようなタブ混入は既知の1箇所として記録されているが、これはスペース4つが多数派である以上、遭遇したら直してよい対象）。
- **セミコロン**: 文末には基本的に付ける。`throw new Error(...)`の直後などで付け忘れが散発する、という既知の傾向があるので、対象ファイル内で見つけたら多数派ルール（付ける）に合わせて補う。
- **クォート**: `import`文のモジュールパス（`"../foo"`）は二重引用符、それ以外の文字列リテラル（エラーメッセージ・イベント名・シェーダキー名など）は単一引用符、という使い分けに統一する。
- **空行**: import群とクラス宣言の間に1行、メソッドとメソッドの間に1行。コンストラクタ内のプロパティ初期化はまとめて隣接させる。それ以外の余分な連続空行・行末の余分な空白は削除する。
- **import順**: モジュールパス文字列のアルファベット順に近い並びに揃える（`MaterialFactory.ts`が模範例）。

### 2.5 触ってはいけないもの（規約が「揺れ」と明記している事項）

`.claude/rules/general.md`「未解決・揺れがある事項」に挙がっている項目は、多数派ルールが確定していないものと、そもそもフォーマットの範囲を超えてAPI/挙動に踏み込むものが混在している。それぞれ扱いが違うので区別すること:

- **`public`修飾子の明示/省略**: 多数派が定まっていないためこのスキルでは統一しない。既存ファイルがどちらの流儀かをそのまま維持する。
- **`Constants`接尾辞の有無**（`RenderTagConstants`はあり、`MouseButton`はなし）・**getter/setterの方式混在**（アクセサ形式 vs `getXxx()`/`setXxx()`、詳細は`vector-matrix.md`）: これらは見た目の整形ではなく命名・APIの選択そのものなので、そもそも`glspinner-tidy`の範囲外。気づいても勝手に変更しない（呼び出し元の書き換えが必要になり「挙動を変えない整形」の枠を超える）。
- **等価比較演算子（`==`/`!=` vs `===`/`!==`）**: 多数派は`==`/`!=`だが、`SceneNode.ts`（同一ファイル内で両方）や`RenderTarget.ts`（`===`/`!==`）のように混在するファイルが複数あり、プロジェクト全体で「`==`に統一されている」というのは実態より強い言い方だった（`general.md`参照）。tidyスキルはどちらか一方に寄せる書き換えを行わない。「厳密比較に直す方がベタープラクティス」という一般常識で`===`へ書き換えるのも、逆に「規約だから」と`==`へ書き換えるのも、**どちらもこのスキルの対象外**（`==`と`===`は型強制の有無で挙動が変わりうるため、そもそも「意味を変えない整形」の定義に収まらない）。

### 3. 挙動が変わっていないことの確認

整形は原則コンパイル結果・実行結果に影響しないはずだが、念のため以下を確認する:

- 変更ファイルに対応する型チェック（`tsc`）が通ること
- `tests/`に対応するテストがあれば`npm test`で確認すること

差分を確認し、フォーマット以外の変更（うっかりロジックを変えていないか、`==`/`===`を無自覚に入れ替えてしまっていないか）が紛れ込んでいないかを見直す。

### 4. 完了後

整形した箇所のサマリ（例: 「インデントを4スペースに統一、セミコロン欠落を3箇所追加」等）を簡潔に報告する。規約自体に判断が割れる書き方を見つけた場合は、`glspinner-conventions`での規約更新を提案する。
