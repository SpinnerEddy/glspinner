# glspinner-context

glspinnerのどのSKILLからでも呼ばれる共通の下準備手順。実装・設計・レビュー・整理整頓・ドキュメント化・コードリーディングなど、対象コードに触れる作業はすべて「今どういう設計になっているか」「どういう規約があるか」を把握してから始めた方が事故が少ない。ここでその下準備を一箇所にまとめておき、各SKILLはこのファイルを読んで手順を実行するだけで済むようにする。

対象トピック: `$ARGUMENTS`

（トピックが空の場合は、直前の会話で話題になっている機能やファイルをトピックとみなして進める。それも判断できない場合はユーザーに一言確認する。)

## 手順

### 1. 設計・規約の把握（.claude/rules/）

アーキテクチャ解説（シーングラフ、レンダリングパイプライン、マテリアル/メッシュ/シェーダー、入力、オーディオ、ツール群、既知のパターン/逸脱）と規約は、以前は`claude_io/design.md`（アーキテクチャ）と`.claude/rules/`（規約）に分かれていたが、内容が地続きだったため2026-07に`.claude/rules/`へ一本化された。`glspinner-conventions`SKILLが管理している「実質的な設計・規約の一次情報源」で、ESLint/Prettierのような自動整形ツールがこのプロジェクトには入っていないため、命名規則・空白やインデントの流儀・import順・ファイル配置ルールに加え、アーキテクチャ上の設計パターン（`Operation`+`Base`二層構造、Factory/Loaderのキャッシュパターン、`RenderTag`+Slotベースのリソースプールなど）もここに人力で言語化されている。

手順:

1. `.claude/rules/general.md`を読む。プロジェクト概要・ディレクトリ構成と責務マップ・横断的な命名/フォーマット/import/コメント方針・未解決事項に加え、冒頭にファミリーファイル一覧の索引がある。
2. トピックが特定のクラス（例: `PhongMaterial`を触る）に関わる場合、そのクラスの接頭辞・接尾辞が一覧のどのファミリーに該当するか確認し、該当ファイル（例: `material.md`）も読む。`Operation`+`Base`二層構造そのものの適用可否や、標準形から外れる例外的な小規模ファミリー（Application/Clock/Scene/Light等）については`operation-base.md`を読む。パイプライン全体の流れ（オーケストレーション・Flow・ポストエフェクト・RenderTarget）を把握したい場合は`pipeline.md`→`flow.md`→`pass.md`→`render-target.md`の順に読むと繋がりが掴みやすい。
3. トピックがどのファミリーにも該当しない一回限りのクラス（`MathUtility`等）を触る場合は`general.md`の内容のみで十分。

`.claude/rules/`自体が存在しない場合は「設計・規約ドキュメント未整備」と明記した上で、`src/`のディレクトリ構成や、これから触るファイルと同じディレクトリ内の既存ファイルを2〜3個直接Glob/Readし、そこから暗黙の設計・規約（インデント幅、セミコロンの有無、命名の傾向など）を推測する。推測であることを出力に明示する。

### 2. 関連ファイルの特定

トピックに応じて `src/` をGlob/Grepし、以下を洗い出す:

- 直接変更・参照することになりそうなファイル
- 同じ設計パターン（Operation+Base、Factory登録など）を先に採用している既存クラス。真似すべき「お手本」として使う
- 呼び出し元・呼び出し先（そのクラスがどこから使われ、何を使っているか）

ファイル数が多くなりすぎる場合は、トピックとの関連度が高いものから5〜10件程度に絞る。

### 3. コンテキストダイジェストの出力

以下の定型フォーマットで出力する。後続の作業（設計・実装・レビューなど）がこのダイジェストだけを見て要点を掴めるようにすること。長々とした説明ではなく、箇条書きで簡潔に。

```
## コンテキストdigest: <topic>
- 関連モジュール: <ディレクトリ/サブシステム名>
- 関連ファイル: <path> — <役割の一言説明> （複数列挙）
- 適用すべき設計パターン: <.claude/rules/該当ファイルから> — なぜそのパターンに従うべきか一言
- 規約上の留意点: <.claude/rules/general.mdおよび該当ファミリーファイルのルール、または「未整備のため周辺コードから推測: ...」>
- 参考にすべき類似実装: <path> — <どこが参考になるか>
```

このダイジェストを出したら、呼び出し元のSKILLの本来の作業（設計する、実装する、レビューするなど）に進む。ダイジェスト自体はゴールではなく、以降の作業の精度を上げるための土台。
