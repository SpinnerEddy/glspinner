# glspinner-reading

## このスキルの立ち位置

`/glspinner-context`は他のSKILL（実装・レビューなど）が下準備として使う、簡潔な箇条書きダイジェストを作るためのcommand。対してこのスキルは、**コードを読んで理解すること自体がユーザーのゴール**であるときに使う。アウトプットは箇条書きの要約ではなく、ユーザーが「なるほど、そういう仕組みか」と腹落ちできる説明。ユーザーの前提知識（WebGLに詳しいか、このプロジェクトの他の部分をどれだけ知っているか）に応じて説明の深さを調整する。

## 実行手順

### 1. 読む対象と、ユーザーが知りたいことの粒度を確認する

「クラス全体の役割を知りたい」のか「特定のメソッドの中身を知りたい」のか「なぜこう実装されているのか（設計意図）を知りたい」のかで説明の組み立て方が変わる。曖昧なら最初にどのレベルの説明が欲しいかを軽く確認してよい。

### 2. 前提となる設計・規約を把握する

`.claude/rules/general.md`と対象に関連するファミリーファイル（`operation-base.md`、`material.md`、`node.md`等）を読み、対象がアーキテクチャ全体のどこに位置づくかを掴む。孤立したコードとして読むのではなく、`XxxOperation`/`BaseXxx`のような全体パターンに当てはめて説明できるようにしておく。

### 3. 実際にコードを辿る

- 対象クラス・関数の定義を読む
- 呼び出し元（誰がこれを使うか）と呼び出し先（これは何を使うか）をGrep/Readで辿り、実行時のデータの流れを掴む
- 継承関係がある場合（`BaseXxx`→具象クラス）は、共通実装がどこにあり具象クラスが何を差分として持つかを整理する
- 一見不可解な書き方（`Scene.run()`のコメントアウトされた間引き描画ロジック、`==`/`!=`が全体で使われている点など）があれば、READMEの課題セクションや`.claude/rules/`配下（`general.md`「気づきにくい挙動」「未解決・揺れがある事項」、`operation-base.md`「小規模ファミリー」、該当ファミリーファイル）の記述に説明がないか確認し、意図的な未完成・規約なのか単なる書き忘れなのかを区別して伝える。一般的なJS/TSの慣習と違う書き方に読者が「バグでは」と戸惑いそうな箇所（`==`の使用など）は、規約として意図的であることを先回りして補足すると親切。

### 4. 説明の組み立て方

- 該当箇所は`path/to/file.ts:行番号`の形式で示し、ユーザーがすぐ実物を確認できるようにする
- コードの丸写しではなく、要点となる数行だけを引用し、そのコードが「何をしているか」ではなく「なぜそうなっているか・全体のどこで効いてくるか」を中心に説明する（「何をしているか」はコード自体が示している）
- 実行フローが複数ステップにまたがる場合は、番号付きの手順や簡単な矢印表記（`A → B → C`）で流れを可視化する
- 設計上の意図（`.claude/rules/operation-base.md`等に記載のパターンなど）と、たまたまそうなっているだけの実装詳細を区別して伝える

### 5. 保存が必要な場合

チャット上での説明で完結するのが基本で、ファイル保存は必須ではない。ただしユーザーが「まとめて残しておいて」「ドキュメント化して」のように保存を望んだ場合は、`claude_io/`配下にmdファイルとして保存する（コードリーディングという行為の成果物であり、`.claude/rules/`のような規約の一次情報源でも、`.claude/skills/`のようなSKILL定義でもないため）。ファイル名はユーザーと相談するか、対象クラス・トピック名から`claude_io/reading-<topic>.md`のような名前を提案する。内容が「今後この種のクラスを追加するときに従うべき規約・アーキテクチャパターン」として恒久的に残す価値があるものなら、一回限りの読み解きメモとして`claude_io/`に置くのではなく`glspinner-conventions`経由で`.claude/rules/`配下への反映を検討する。

### 6. 完了後

説明した範囲に隣接する「ついでに知っておくと理解が深まる箇所」があれば一言添えてよいが、ユーザーが聞いていない範囲まで広げすぎない。関連して未実装・矛盾に気づいた場合は`glspinner-task-discovery`、実際に手を入れたくなった場合は`glspinner-implement`を案内する。
