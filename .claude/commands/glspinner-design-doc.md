# glspinner-design-doc

`glspinner-design-doc`SKILLが持つ「設計提案をファイルへ書き出す」処理そのものを、`glspinner-context`/`glspinner-ideas`と同型でcommand化したもの。単体のSKILLからだけでなく、`glspinner-design`SKILLが設計合意直後にそのまま書き出したい場合にも呼ばれる共通処理のため、独立したcommandとして持つ。

対象トピック: `$ARGUMENTS`

（トピックが空の場合は、直前の会話で固まった設計、または`glspinner-design`が承認したプランファイル（`~/.claude/plans/*.md`）の内容からトピック名を推定する。判断できない場合はユーザーに一言確認する。）

## 前提: `design/`フォルダの位置づけ

このリポジトリのドキュメントは3つの軸に分かれる。書き出す前に必ず区別すること。

| 場所 | 軸 | 担当 |
|---|---|---|
| `docs/` | 「今、何が実装されているか」のスナップショット | （既存の一括ドキュメント化作業） |
| `.claude/rules/` | 「コードを書くときに従うべき規約」＝コードに実際に宿っているパターンの記録 | `glspinner-conventions` |
| `design/` | 「これから何を作るか」の**未実装の設計提案** | このcommand |

**`design/`配下には未実装の内容しか書かない。** 実装済みのパターンを書きたい場合は`.claude/rules/`（`glspinner-conventions`の担当）へ誘導し、このcommandでは対応しない。

## 手順

### 1. `design/`フォルダの現状確認

- `design/`フォルダと`design/README.md`が存在するか確認する。
- 存在しない場合は新規作成する。`design/README.md`には以下を含める（[`design/README.md`](../../design/README.md)が既にあればそれを踏襲・追記する。無ければ以下の骨子で新規作成する）:
  - `design/`の位置づけ（上記の3軸比較表）
  - ドキュメント一覧（トピック名・対象ファイル・ステータスの表）
  - 実装完了後は該当ドキュメント冒頭に実装済みの旨を追記し、内容を`docs/`と`.claude/rules/`へ反映する運用メモ
- 存在する場合は既存の`design/README.md`を読み、ドキュメント一覧に対象トピックの行があるか（＝新規提案か、既存提案の改訂か）を確認する。

### 2. トピック文書の作成・更新

ファイル名は`design/<topic-slug>.md`（kebab-case、内容を表す短い名前）。

新規作成の場合、以下を目安にした章立てで書く（対象の性質に応じて過不足あってよい。固定テンプレートを機械的に当てはめない）:

```markdown
# <設計タイトル>

**ステータス**: 提案（未実装）
**対象**: <関連する src/ 配下のパス>

## Context（なぜこの変更をするか）
（現状の問題点・出発点。具体的なファイル名・行番号を伴わせ、後から読み返しても意味が通るようにする）

## 決定事項（会話で合意済み） ※複数の論点を検討した場合のみ
（論点と決定を表で整理）

## 設計
（クラス構成・インターフェース案・既存ファミリーとの接続点。コードスニペットを添える）

## 変更対象ファイル
（新規/書き換え/削除/スコープ外を分けて列挙）

## 実装順序 ※規模が大きい場合のみ

## 検証方法
（ユニットテスト観点、実機確認観点）

## 実装分担についての注意 ※src/配下やexamples/配下に触れる設計の場合のみ
`.claude/CLAUDE.md`の編集範囲制限（`src/`/`examples/`は原則ユーザー実装、Claude Codeが担当できるのは`tests/`・`.claude/rules/`・レビュー/設計相談）に触れておく。

## この提案の経緯
（どういう会話・検討を経てこの結論になったか。却下した代替案とその理由も残す）
```

既存提案の改訂の場合は、上書きせず末尾に`## 変更履歴`節（`.claude/rules/`各ファイルの運用に合わせる）を追記し、何が・なぜ変わったかを記録する。

### 3. `design/README.md`のドキュメント一覧を更新

新規作成なら行を追加、改訂なら既存行のステータス・説明を更新する。

### 4. 完了報告

作成・更新したファイルパスを呼び出し元へ返す。次にどうするか（実装に進む／規約への反映は実装後）の案内は呼び出し元SKILL側の役割なので、このcommand自体はファイル作成の完了をもって終了とする。
