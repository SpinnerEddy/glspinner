# glspinner-task-discovery

## このスキルの立ち位置

このスキルは「ゼロから発想する」のではなく「すでにコードの中に痕跡が残っている、やり残しの棚卸し」をする。glspinnerは個人開発中のプロジェクトで、意図的に未完成のまま放置されている部分（空のFactoryファイル、コメントアウトされたimport、READMEのTODOリストなど）がいくつもある。それらを漏れなく拾い上げ、優先順位をつけて提示することがゴール。

「こんな機能があったら面白いのでは」という創造的な提案は範囲外（`glspinner-ideation`の仕事）。ここで扱うのは、すでに何らかの形でコード上に「やりかけ」の証拠があるものに限定する。

## 収集手順

以下のソースを横断的に確認する。全部を毎回深掘りする必要はないが、少なくとも1〜4は必ず確認すること。

1. **README.md**: 「次やること」「その後」「課題」に類する見出しを探し、記載内容を拾う。
2. **`.claude/rules/`配下に記録された「未完成・実験的な部分」**: `general.md`「気づきにくい挙動」（`LightFactory`空ファイル、`MidiDevice`のスタブ実装等）、`operation-base.md`「小規模ファミリー」（Light系が単独実装のまま等）、各ファミリーファイルの例外・未活用記述（`pipeline.md`のRenderTag未使用値、`render-target.md`のCustomRenderTarget未活用、`device.md`のMidiDevice詳細等）を拾う。
3. **TODO/FIXME/XXXコメント**: `src/` を `TODO|FIXME|XXX` でgrepする。
4. **空ファイル・スケルトンファイルの検出**: `src/` 配下でファイルサイズが極端に小さい、またはexportのみで中身がないファイルをGlob/Grepで探す。
5. **無効化されたコード**: コメントアウトされたimport文（「今は繋いでいない」ことを示す慣習が`.claude/rules/general.md`の「import / ファイル配置」に記載されている）。
6. **配線されていない実装（サイレントなデッドコード）**: これが最も見落としやすく、かつ価値が高い。「空ファイル」や「コメントアウト」のように見た目でわかる未完成とは違い、**中身は実装済みなのに、それを呼び出す経路がどこにも存在しない**というパターンがglspinnerには潜んでいる（例: `setLights()`のような設定用メソッドが定義・呼び出し先の両方は揃っているのに、間をつなぐ「呼び出す側」のコードが一つもない）。調査対象の主要クラス・サブシステムについて、「これが持つ公開メソッド（特に`setXxx`/`initialize`/`register`のような設定・初期化系）は、実際にどこかから呼ばれているか」を`grep`で追跡する一手間を必ずかける。呼び出し元が見つからなければ、それは単なるスタイルの問題ではなく「機能として動いていない」可能性が高い、優先度の高い発見になる。README・`.claude/rules/`に書かれていない、コードを実際に追跡しないと見つからない類のギャップなので、他の項目より念入りに確認する価値がある。
7. **`.claude/rules/general.md`や各ファミリーファイルの「未解決・揺れがある事項」**: 直接のバグではないが、技術的負債として一覧に含めてよい（優先度は低めに）。
8. **テストカバレッジのギャップ**: `tests/` 配下のディレクトリ構成と `src/` を見比べ、テストが1つも存在しないモジュール群（例: renderer/webgl系）を洗い出す。ただし「WebGLコンテキスト依存でユニットテスト化しづらい」という構造的事情もあるため、テストがない=即問題、とは決めつけず一言添える。

このプロジェクトに `.claude/rules/` がまだ存在しない場合は、その旨を伝えた上で `src/` を直接調査する。

## スコープの絞り方

ユーザーの質問がプロジェクト全体を指している場合（「未実装の機能を洗い出して」等）は上記1〜8を広く確認してよい。一方、ユーザーの質問が特定の機能・クラスに絞られている場合（「MidiDeviceまわりで何かやり残しはある？」等）は、回答もその話題に集中させる。調査の過程で無関係な発見（例: MidiDeviceを調べていて`LightFactory.ts`の空ファイルに気づいた、など）があっても、基本的には報告に含めない。ユーザーが明示的に「他にも気になる点があれば教えて」と言っている場合や、その発見が今回のテーマと直接関係する場合を除き、話題を広げるより深く掘ることを優先する。

## 優先度の付け方

- **高**: コア機能に影響する・複数の他機能から参照される・すでに壊れている挙動がある
- **中**: 機能として独立している未実装（例: 特定デバイスクラス1つの未実装）で、放置していても他に影響しない
- **低**: スタイルの揺れ、コメント・ドキュメントの不足など、動作に影響しない事項

優先度だけでなく、ユーザーが直近の会話で触れているテーマがあれば、それに関連する項目を上位に引き上げてよい。

## 出力フォーマット

優先度（高→中→低）でグルーピングしたMarkdownの箇条書きで報告する。各項目には次を添える:

```
- **[項目名]** — なぜ気になるか（一言）／関連ファイル: path/to/file.ts
```

ファイルへの保存は必須ではない。チャット上での報告で十分な場合が多いが、ユーザーが「保存して」「リストにして残しておいて」と言った場合は `claude_io/` 配下に保存する（ファイル名はユーザーと相談するか、`task-list.md` を提案する）。

## 完了後

洗い出した項目のうち、次にどれから着手するかをユーザーに一言確認する。設計を詰めるなら`glspinner-design`、すぐ実装に入るなら`glspinner-implement`へ引き継ぐとよい、と案内する。
