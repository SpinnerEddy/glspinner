# glspinner-review

## このスキルの立ち位置

`/code-review`（汎用）は正しさ・再利用性・簡潔性・効率という観点でコード全般を見る。このスキルはそれを代替するのではなく、glspinnerというプロジェクトに固有の「アーキテクチャ規約に沿っているか」というレンズを追加するもの。両方の観点が必要な場合は、`/code-review`とこのスキルを両方使うようユーザーに案内してよい（このスキル単体でバグ検出まではカバーしない）。

## 実行手順

### 1. レビュー対象の特定

デフォルトでは現在のワーキングツリーの差分（`git diff`）をレビュー対象とする。ユーザーが特定ファイル・関数を指定した場合はそちらを優先する。

### 2. コンテキストダイジェストの取得

`/glspinner-context <対象トピック>` を実行し、対象領域で参照すべき規約・お手本実装を把握する。

### 3. glspinner固有の観点でチェックする

- **命名・フォーマット規約**: `.claude/rules/general.md`の命名規則・フォーマット・importルール、および対象クラスが属するファミリーファイル（`material.md`/`device.md`等、`general.md`冒頭の索引を参照）に沿っているか。特に見落とされがちな点として、`private`/`protected`プロパティに`_`接頭辞を付けていないか、説明的なJSDocを新規に足していないか（JSDocを書く慣習自体が存在しない）を確認する。等価比較演算子（`==`/`!=` vs `===`/`!==`）はプロジェクト全体で厳密に統一されていないため指摘対象にはしないが、対象ファイル内で急に書き方が変わっている（それまで`==`だったファイルに`===`が1箇所だけ混じる等）場合はファイル内の一貫性という観点で指摘してよい。一般的なTypeScriptの「良い書き方」に寄せた結果、glspinnerの規約から外れているコードは見つけやすい典型パターンなので重点的に見る。
- **Operation+Baseパターンの適用妥当性**: 新規クラスが`XxxOperation`インターフェース + `BaseXxx`抽象クラスを必要とする性質（差し替え可能性・バリエーションの見込み）を持つのに素の具象クラスとして書かれていないか。逆に、単純な一回限りの実装にわざわざ不要な抽象化を足していないか（過剰設計側の逸脱もチェックする）。
- **疎結合機構との整合性**: レンダリング関連の変更なら、`RenderTag`・`RenderTargetRegistry`のスロット・`RendererContext`のグローバルUniformといった既存の宣言的な繋ぎ方を迂回して、シーングラフやRTの実体を直接掴むような密結合な書き方をしていないか（`.claude/rules/pipeline.md`・`render-target.md`に記載の設計思想からの逸脱）。
- **Factory/Loaderキャッシュの一貫性**: マテリアル相当の新規追加が`MaterialFactory`経由になっているか、既存のキャッシュ機構と矛盾する独自ロード処理を増やしていないか。
- **未完成領域の悪化**: `LightFactory`空ファイルや`MidiDevice`未実装のような既知のギャップ（`glspinner-task-discovery`が扱う領域）を、今回の変更が意図せず広げていないか（例: 空のFactoryに依存する新規コードを足してしまっている等）。
- **既存の「揺れ」との整合**: `.claude/rules/general.md`の「未解決・揺れがある事項」、または対象ファミリーファイルに記載の固有の揺れ・例外に該当する場合、今回の変更がどちらの流儀に寄せているかを確認し、無自覚に両方が混在しないようにする。

### 4. 出力フォーマット

指摘事項ごとに以下の形式で列挙する。指摘がなければ「glspinner固有の観点では問題なし」と明記する。

```
- **[ファイル:行]** 指摘内容 — 何の規約・パターンに対してどう外れているか／どう直すべきか
```

深刻度は「規約違反（明確に直すべき）」「設計判断が割れる（要確認）」の2段階で十分。バグの可能性に気づいた場合も報告してよいが、その場合は「これは正しさの観点なので`/code-review`でも確認することを推奨」と一言添える。

### 5. 完了後

修正が必要な指摘があれば、ユーザーの了承を得てから`glspinner-implement`または直接編集で対応する。
