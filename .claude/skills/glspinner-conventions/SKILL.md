# glspinner-conventions

## このスキルの立ち位置

glspinnerには`eslint.config.mjs`/`.prettierrc.json`（`glspinner-linter`スキルにより導入済み）があるが、機械的に強制しているのはクラス/インターフェース命名など規約のごく一部のみ（詳細は`.claude/rules/general.md`「この文書について」節）。大半の「規約」は誰かが書いたルールブックとしては存在せず、既存コードの書き方そのものが規約になっている。このスキルの仕事は、そのコードに宿っている暗黙のルールを読み取って`.claude/rules/`配下のmdファイル群として言語化し、以後の作業（実装・レビュー・整理整頓）がブレなく従えるようにすることです。

一度作って終わりではなく、ユーザーから「このルールを追加したい」「この書き方に変えたい」「新しいクラスファミリーができたので規約を足したい」という改訂依頼が来たら、そのつど更新していくドキュメント群として扱う。

## ドキュメント構成

規約は単一ファイルではなく、`.claude/rules/`配下に**クラスファミリー単位**で分割して置く。ファミリーとは「接頭辞・接尾辞を共有するクラス群」のこと（例: `~Material`, `~Device`, `~Node`, `~Mesh`, `~Pipeline`, `~Pass`, `~Flow`, `~Buffer`, `Base~`）。2026-07時点の構成:

| ファイル | 内容 |
|---|---|
| `general.md` | どのファミリーにも紐づかない横断規約（命名一般・フォーマット・import・コメント方針・未解決事項・変更履歴） |
| `operation-base.md` | `XxxOperation`+`BaseXxx`二層構造のメタパターンそのものの適用基準、Factory/Loaderとの使い分け、標準形から外れる小規模ファミリー（Scene/Light等）のまとめ |
| `application.md` | `~Application`ファミリー（`BaseApplication`/`RecordingApplication`の2段中間抽象クラス） |
| `clock.md` | `~Clock`ファミリー（`ClockOperation`→`Clock`という`BaseClock`ではない命名の抽象クラス） |
| `material.md` | `~Material`ファミリー |
| `device.md` | `~Device`ファミリー |
| `node.md` | `~Node`ファミリー |
| `mesh.md` | `~Mesh`ファミリー |
| `pipeline.md` | `~Pipeline`ファミリー |
| `pass.md` | `~Pass`（ShaderPass）ファミリー |
| `flow.md` | `~Flow`（RendererFlow）ファミリー |
| `buffer.md` | `~Buffer`ファミリー |
| `geometry.md` | `~Geometry`系（`Plane`/`Torus`等）ファミリー |
| `render-target.md` | `~RenderTarget`ファミリー |
| `vector-matrix.md` | `Vector`/`Matrix`系（自己参照ジェネリクスの独自パターン） |
| `audio.md` | `AudioOutput`/`AudioInputOperation`系 |
| `tools.md` | `Recorder`/`GuiUtility`/`*GuiController`系（静的クラス+`initialize()`パターン） |
| `shader.md` | `src/webgl/shader/`配下のGLSLシェーダー（TypeScriptのクラス構造とは無関係な唯一のファミリー） |

`.claude/rules/`配下のファイルはSKILL/commandではなくプレーンな参照ドキュメントなのでfrontmatterは付けない（各SKILLの実行手順から明示的に読みに行く前提）。ファミリーを持たない一回限りのクラス（`MathUtility`, `ColorUtility`, `*Loader`, `MaterialFactory`, `ShaderProgram`, `ShaderAttribute`, `ShaderUniform`等）は専用ファイルを持たず、`general.md`の横断規約のみに従う。`Camera`/`Transform`/`SceneGraph`は`node.md`、`Recorder`/`*GuiController`は`tools.md`にそれぞれ周辺クラスとして含まれる（家族を持たない一回限りのクラスと、周辺クラスとして既存ファイルに含めるクラスの違いは、関連する既存ファミリーが近くにあるかどうかで判断する）。

なお、以前は`claude_io/design.md`という別ファイルにアーキテクチャ解説を置いていたが、内容の性質が規約と地続きだったため2026-07に`.claude/rules/`へ統合し廃止した。プロジェクト概要・ディレクトリ構成と責務マップは`general.md`冒頭、アプリケーションライフサイクルは`application.md`に移設済み。今後「アーキテクチャの解説」に類する内容を追加する場合も、新しい別ファイルを作らずこのSKILLが管理する`.claude/rules/`配下に統合する。

## 実行手順

### 0. モードの確認

新規ファミリーファイルの新設・既存ファイルの再編・`general.md`の構成変更など、**規約ドキュメントの構造判断を伴う場合**は、まず`EnterPlanMode`でプランモードに入り、手順1〜3（現状把握・ファミリー判定・規約抽出）をプランモードのまま進める。手順4の書き込みに入る前に`ExitPlanMode`で合意を取る。既存ファイルへの追記だけで済む改訂ならプランモードは不要。

### 1. 現状の把握

- `.claude/rules/`配下の既存ファイル一覧を確認し、今回の依頼がどのファイルに関わるか（新規ファミリーの追加なのか、既存ファミリーファイルの改訂なのか、横断規約=`general.md`の改訂なのか）を判断する。
- ユーザーから具体的な改訂依頼（「このルールを足したい」「この書き方はやめたい」等）が来ている場合は、それを最優先の入力として扱う。ユーザーの明示的な指示は、以下で観察するコード上の慣習より優先する。
- 今回の改訂対象が`general.md`のようなプロジェクト概要寄りの事実（導入済みツール、コマンド一覧、既知の未解決事項等）の場合、`.claude/CLAUDE.md`にも同じ事実が別の言葉で書かれていないか確認する。書かれていれば、そちらの陳腐化は自分では直さず`glspinner-document`への引き継ぎが必要になる（2026-07、ESLint/Prettier導入状況の説明がCLAUDE.mdと`general.md`の両方に重複して書かれ、同時に陳腐化した実例があったための運用）。

### 2. どのファイル（ファミリー）に属するかを判定する

- 対象クラス名に既存ファミリーと同じ接尾辞・接頭辞があるか確認する（例: `~Material`という名前が付くクラスなら`material.md`）。
- 接尾辞・接頭辞があっても、そのクラスが`XxxOperation`+`BaseXxx`の標準形に従っているとは限らない（`operation-base.md`に記録した通り、`Clock`や`Scene`のように`Base`接頭辞を使わない例外や、`BaseSceneRendererFlow`のようにファミリー通称と異なる命名の例外が複数ある）。実際のインターフェース・抽象クラスを読んで確認し、標準形どおりなら該当ファミリーファイルへ、独自の変則パターンなら`operation-base.md`の「小規模ファミリー」節に追記するかを判断する。
- 該当する既存ファミリーがなく、かつ同じ接尾辞・接頭辞を共有する具象クラスが複数（目安2つ以上）ある場合は、新しいファミリーファイルを作る。ファイル名はファミリー呼称のkebab-case（例: `~Light`ファミリーを独立させるなら`light.md`）。作成したら本SKILLの「ドキュメント構成」表と、`.claude/rules/general.md`冒頭の説明に追記する。
- 具象クラスが1つしかない、またはそのクラス特有の観点で切り出すほどの分量がない場合は、無理に新規ファイルを作らず`operation-base.md`の「小規模ファミリー」節、または`general.md`に短く追記するに留める。

### 3. 実コードからの規約抽出

`.claude/rules/general.md`冒頭の「ディレクトリ構成と責務マップ」を読み、モジュール構成を把握した上で、対象ファミリーの`XxxOperation`インターフェース・`BaseXxx`抽象クラス・具象クラス2〜3個を実際に読む。既存ファイル（`.claude/rules/material.md`等）の書き方を手本にし、以下を必ず含める:

- そのファミリーの`Operation`/`Base`/具象クラスの実際のコードスニペット（丸写しではなく要点を抜粋）
- `Base`側が共通実装を持つか、単なる`abstract`宣言の集合（薄いBase）かの区別
- 具象クラス間で共有されている定型パターン（新規追加時にコピー元にできる実装）
- そのファミリー固有の例外・非対称性（`operation-base.md`や既存ファイルの「例外」記述と同じ粒度で、標準形から外れている点があれば正直に記録する。glspinnerのコードはこの手の例外が多く、それを隠さず書くことこそがこの規約群の価値になっている）

観察結果が割れている（ファイルによって流儀が違う）場合は、それを規約書に「揺れがある」と正直に記録し、多数派を暫定ルールとして採用するかユーザーに確認する。無理に統一ルールをでっち上げない。等価比較演算子（`==`/`!=`と`===`/`!==`の混在）のように、過去の整理で「一貫している」と判断したものが実際にはファイルによって違ったというケースもあるため、既存ファイルに書かれた結論を鵜呑みにせず、新規に確認したコードと突き合わせる。

### 4. `.claude/rules/`配下ファイルの作成・更新

- 対象ファイル（`general.md`、`operation-base.md`、または該当ファミリーファイル）のみを更新する。無関係なファイルは触らない。
- 既存ファイルを更新する場合、無関係な既存記述を消さない。新規ファイルを作る場合は以下の章立てを目安にする（ファミリーの実態に合わせて過不足あってよい）:

```markdown
# `~Xxx` ファミリー規約

## 構成
（Operation/Base/具象クラスの一覧とファイルパス）

## `BaseXxx`が提供する共通実装
（コードスニペット）

## 具象クラスの実装パターン
（コードスニペット、新規追加時に手本にすべき定型）

## このファミリー固有の揺れ・例外
（あれば）

## 他ファミリーとの関係
（依存・委譲関係）
```

- 各ファイルの末尾に変更履歴を残す場合は、そのファイル内に短く追記する（プロジェクト全体で1つの変更履歴に集約しない。ファイルが分割されているため、変更履歴もファイル単位で追う方が追跡しやすい）。

### 5. ユーザーへの報告

規約書のフルテキストを再掲する必要はない。どのファイル（ファミリー）を新規作成・更新したか、何を新規に決めたか、判断が割れて保留にした事項があるかを簡潔に伝える。手順1で`.claude/CLAUDE.md`側の陳腐化に気づいた場合は、それも併せて伝えて`glspinner-document`への引き継ぎを案内する。
